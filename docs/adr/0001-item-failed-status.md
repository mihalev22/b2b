# ADR 0001: статус позиции `failed` и счётчик `failed_count`

Статус: предложен, ждёт согласования архитектора (Артас) и владельцев фронта (Лёша) и ml (Егор).

## Контекст

Сейчас у позиции статусы `pending | auto | needs_review | accepted | corrected`. Если классификация
одной позиции падает (ошибка ml, таймаут, исключение), вся задача уходит в `failed`, и остальные
позиции не получают результата. Фронт не может показать «эта строка не обработалась», а
`failed_count` у задания всегда 0.

## Решение

1. В `ItemStatus` добавляется значение `failed`.
   - Позиция получает `failed`, если её классификация упала (исключение или ошибка ml после ретраев).
   - У такой позиции `ktru_code` и `ktru_name` пустые, `confidence` пустой, `candidates` пустой.
2. Задание:
   - при падении отдельных позиций остаётся `done`, воркер считает `failed_count` (число позиций со статусом `failed`);
   - `failed` у задания — только если упал весь файл (разбор, превышение лимита, отсутствие файла).
3. Новое необязательное поле у позиции: `failure_reason` (строка до 255 символов), причина падения
   для показа в таблице. Существующие поля не меняются.
4. Фильтр `GET /jobs/{id}/items?status=failed` работает через уже существующий параметр `status`.
5. Миграция `0003`: поле `failure_reason`, без изменения данных.

## Последствия

- Контракт меняется: `docs/api/openapi.yaml` перегенерируется (`python backend/scripts/export_openapi.py`).
- Фронт: обновить копию контракта `frontend/openapi.yaml`, `npm run gen:api`, добавить цвет и подпись
  для `failed` в `statusColor` и `texts.itemStatus` (делает Лёша).
- Счётчики `JobOut` получают `failed_count` (уже есть в схеме, теперь заполняется).
- ml: ошибка по позиции не должна ронять задание; `/classify` должен отдавать `needs_review` и зону.

## Альтернативы

- Считать упавшие позиции `needs_review` с пустым кодом. Отклонено: человек не отличит «низкая
  уверенность» от «не обработалось», а фронт не сможет показать ошибку.
- Отдельная таблица ошибок. Отклонено: лишний JOIN ради одного статуса.
