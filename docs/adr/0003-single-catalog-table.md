# 0003. Один каталог КТРУ: таблица `ktru_position` с векторами, поиск делает ml
Статус: предложено · 2026-10-10 · Артас (архитектор)

## Контекст

Сейчас в команде два разных каталога КТРУ, и ни один не подходит для MVP целиком.

| | Женя: `ktru_position` в нашей БД | Кирилл: `public.ktru` в своей БД |
|---|---|---|
| Источник | сайт tzfz.ru (сторонний), ~60 тыс. кодов | официальные XML-выгрузки, со снимками и версиями |
| Что есть | код, название, ОКПД2; статус всегда `active` | версии, настоящий статус, характеристики, вектор `vector(768)` |
| Как искать | `LIKE`/trgm по названию | косинусная близость векторов `embeddinggemma:300m` |
| Кто может запустить | все (`load_catalog.py`, файл в `data/`) | только Кирилл: база есть лишь на его ПК, скрипта наполнения в репозитории нет |

Последствия текущего положения: бэкенд `/ktru/search` и будущий ml смотрят в разные данные,
настоящие коды (по графику 15–16 октября) никто, кроме Кирилла, не увидит, а пересчитывать
векторы для 60 тыс. позиций каждому участнику на CPU долго.

Отдельно: ml-калибровка Егора в примере использует модель `sergeyzh/BERTA`, а каталог Кирилла
посчитан `embeddinggemma:300m`. Уверенность имеет смысл только для той модели, которой посчитаны
векторы каталога (ADR 0002, веса привязаны к `embedding_model`).

## Решение

1. **Одна таблица — `ktru_position` в общей БД compose** (`pgvector/pgvector:pg16`, база `ktru`).
   Отдельной базы и пользователя `ai_agent` нет.
2. **Источник данных — официальные выгрузки Кирилла.** В таблице одна строка на код:
   последняя версия кода; `status` — настоящий статус из выгрузки. История версий в MVP не хранится.
3. **Миграция `0004`** (бэкенд) добавляет в `ktru_position`:
   - `version` — строка версии;
   - `characteristics` — `jsonb`, характеристики для показа пользователю;
   - `embedding` — `vector(768)`, индекс HNSW (`vector_cosine_ops`);
   - `embedding_model` — строка, например `embeddinggemma:300m`.

   В ORM бэкенда эти колонки не добавляются: бэкенд их не читает, тесты на SQLite не ломаются.
4. **Одна модель эмбеддингов для каталога — `embeddinggemma:300m`.** Префиксы как у Кирилла:
   документ `title: none | text: `, запрос `task: search result | query: `.
   Смена модели — это пересчёт всей колонки `embedding` и повторная калибровка (ADR 0002).
5. **Заливка без пересчёта.** Кирилл один раз выгружает из своей БД файл
   (`code, name, okpd2_code, version, status, characteristics, embedding, embedding_model`),
   файл кладётся на общий диск команды (в git не кладём: размер, скорее всего, сотни МБ).
   `scripts/catalog/load_catalog.py` учится заливать этот файл одной командой, как сейчас.
   Скрипт Кирилла, которым считались векторы (`ktru_migration`), коммитится в
   `scripts/catalog/` — чтобы каталог можно было пересобрать без его ПК.
6. **Поиск кодов делает ml.** `POST /classify`: текст позиции → вектор запроса через Ollama →
   топ-5 по `embedding <=> query` только среди действующих кодов (по `status`) → уверенность и зона Егора
   (ADR 0002). ml читает `ktru_position` по тому же `DATABASE_URL`.
   Воркер бэкенда вызывает ml вместо `LIKE`-поиска; `/ktru/search` и `/ktru/{code}` остаются у бэкенда.
7. **Ollama — отдельный сервис compose** (`ollama/ollama`, модели в томе `models`),
   ml ходит на `http://ollama:11434`.

## Последствия

- Все работают с одним каталогом, настоящие коды видны в общем фронте Лёши, а не только в mini_app.
- Каталог tzfz.ru и `collect_tzfz.py` больше не нужны: заливка идёт из файла Кирилла.
- Из кода Кирилла в ml переносится ядро (вектор запроса + поиск + характеристики),
  без своей очереди, своего сайта и проверок «только localhost / только `ai_agent`».
- LLM-извлечение позиций из PDF/DOCX (qwen) в это решение не входит: xlsx/csv по-прежнему
  разбирает бэкенд построчно. Отдельный ADR, когда дойдём до PDF.
- Если поиск по HNSW окажется заметно хуже точного перебора — сравнить на размеченной выборке
  Егора и решить отдельно.

Кто и к какому сроку:

| Что | Кто | Срок |
|---|---|---|
| Файл выгрузки + скрипт `ktru_migration` в `scripts/catalog/` (PR) | Кирилл | 12.10 |
| Миграция `0004`, `load_catalog.py` под новый файл | Женя | 13.10 |
| `POST /classify` в ml на коде Кирилла, сервис `ollama` в compose | Кирилл + Егор | 15.10 |
| Воркер зовёт ml, `needs_review` и `zone` из ответа | Женя | 16.10 |
| Калибровка на векторах `embeddinggemma:300m` | Егор | до 22.10 |

## Альтернативы

- **Оставить отдельную базу Кирилла, ml ходит в неё.** Отклонено: запустить может только Кирилл,
  бэкенд и ml видят разные данные.
- **Две таблицы: `ktru_position` + `ktru_embedding` по коду.** Рабочий вариант, но для MVP
  лишний join и два загрузчика. Вернёмся, если понадобится держать векторы двух моделей сразу.
- **Хранить все версии кодов, как у Кирилла.** Отклонено для MVP: в закупке нужен действующий
  код, а уникальность `code` уже используют `/ktru/{code}` и загрузчик.
