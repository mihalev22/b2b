# 0002. Зону уверенности и needs_review определяет только ml
Статус: предложено · 2026-10-10 · Егор (ml), по предложению Артаса

## Контекст

Пороги цветовых зон уверенности сейчас зашиты во фронте (`frontend/src/confidence.ts`,
85 и 60), а статус позиции `auto` / `needs_review` бэкенд будет выставлять сам. После калибровки на
размеченной выборке порог высокой зоны может стать выше 85: скрипт выбирает наименьший
порог от 85, при котором среди позиций не ниже порога верных не меньше 85 %. Порог меняется
и при каждой повторной калибровке, например после смены модели эмбеддингов 20 октября.
Если пороги живут в трёх сервисах, они разойдутся.

## Решение

Пороги хранятся только в `ml/app/confidence_params.json`, остальные сервисы берут результат.

Контракт ml, новые необязательные поля:

```
POST /classify
результат позиции: + zone: "high" | "medium" | "low" | "none"
  (needs_review уже есть в контракте)

GET /thresholds
{"high": 85.0, "medium": 60.0, "calibrated": false, "embedding_model": null}
```

Бэкенд:
- `Item.status` ставится из `needs_review`: `needs_review` → `"needs_review"`, иначе `"auto"`;
- новое необязательное поле `zone` в `items` и `ItemOut` (миграция);
- `GET /api/v1/confidence/thresholds` отдаёт ответ ml `/thresholds` фронту.

Фронтенд:
- цвет позиции — из `item.zone`;
- легенда, фильтры и `min_confidence` для массового принятия — из
  `/api/v1/confidence/thresholds`;
- константы в `confidence.ts` остаются только запасным вариантом, когда `zone` нет
  (моки, старые задания).

## Последствия

- Повторная калибровка меняет зоны без правок бэкенда и фронта.
- Зона фиксируется в момент классификации: старые задания не перекрашиваются после
  новой калибровки, это совпадает с уже сохранённым `status`.
- Поле `calibrated` позволяет фронту показать «уверенность ещё не откалибрована».
- Нужны изменения у трёх владельцев: ml (Егор и напарник), бэкенд (Женя), фронт (Лёша).
  Срок — до 22 октября, когда ml отдаёт итоговые пороги.
